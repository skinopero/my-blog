1IoC 컨테이너의 동의어가 아닌 것은?
IoC Container, ApplicationContext, BeanFactory는 전부 같은 것을 가리키는 동의어야. DispatcherServlet은 Spring MVC에서 요청을 분배하는 별개의 개념이야.
2PaymentService가 생성자에서 new KakaoPayGateway()를 직접 호출하는 방식의 문제는 SOLID 중 어떤 원칙을 위반할까?
구현체를 바꾸려면 PaymentService 코드 자체를 고쳐야 하므로, "확장에는 열려있고 변경에는 닫혀있어야 한다"는 개방-폐쇄 원칙을 위반해.
3Spring Bean의 기본 Scope는?
별도로 @Scope를 지정하지 않으면 Bean은 기본적으로 singleton으로 등록돼 — 컨테이너 안에 동일한 인스턴스가 하나만 존재해.
4@Scope("prototype")으로 등록된 Bean의 특징은?
prototype은 요청마다 매번 새 인스턴스를 만들어 반환해. singleton과 정반대야.
5Bean이 상태(필드값)를 가지면 왜 위험할까?
Bean은 하나의 인스턴스를 여러 요청이 공유하기 때문에, 요청별로 달라지는 데이터를 필드에 저장하면 서로 덮어쓰게 돼. 요청별 데이터는 DTO로 주고받아야 해.
6@ComponentScan이 하는 일은?
AppConfig에 @Bean 메소드를 일일이 적지 않아도, @Component/@Service 등이 붙은 클래스를 컨테이너가 알아서 찾아 등록해줘.
7Spring이 공식적으로 권장하는 의존성 주입 방식은?
생성자 주입은 final로 불변성을 보장하고 필수 의존성을 생성 시점에 강제화할 수 있어서 공식 권장 방식이야.
8필드 주입(@Autowired private PaymentInterface p;)의 단점이 아닌 것은?
"선택적 의존관계를 가질 수 있다"는 오히려 setter 주입의 장점이야. 필드 주입의 단점은 final 불가, 그리고 의도치 않게 필드를 재대입해도 컴파일러가 막아주지 못한다는 것.
