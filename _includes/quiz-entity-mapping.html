1@GeneratedValue(strategy = GenerationType.IDENTITY)를 쓰면 persist() 직후 어떤 일이 벌어질까?
IDENTITY는 PK 생성을 DB의 AUTO_INCREMENT에 위임하므로, INSERT를 실행해야만 PK 값을 알 수 있다. 그래서 persist() 즉시 INSERT가 나가고 쓰기 지연이 적용되지 않는다.
2SEQUENCE 전략은 IDENTITY와 무엇이 다를까?
SEQUENCE는 DB의 시퀀스 객체(Oracle, PostgreSQL 등)에서 PK 값만 먼저 받아올 수 있어서, 실제 INSERT는 쓰기 지연 SQL 저장소에 쌓였다가 commit 시점에 반영된다.
3@Column의 nullable, unique, length 같은 속성은 언제 사용될까?
@Column의 속성들은 JPA가 테이블을 생성(DDL)할 때 사용되는 설정이다. 애플리케이션 실행 중 값 검증과는 별개다.
4enum을 @Enumerated(EnumType.STRING) 대신 ORDINAL로 매핑하면 생길 수 있는 문제는?
ORDINAL은 enum의 필드 순서(0, 1, 2...)를 그대로 저장하기 때문에, 나중에 enum 선언 순서가 바뀌거나 중간에 값이 추가되면 기존에 저장된 숫자의 의미가 틀어진다. 그래서 실무에서는 이름을 그대로 저장하는 STRING을 권장한다.
5JDBC 시절의 "DAO"는 Spring + JPA 환경에서 보통 뭐라고 부를까?
JDBC에서 DB 접근 객체를 DAO라고 불렀다면, Spring + JPA 환경에서는 같은 역할의 계층을 Repository로 부른다. DAO == Repository로 인식하면 된다.
6MemberRepository는 내부에서 어떤 방식으로 데이터베이스에 접근할까?
MemberRepository는 @PersistenceContext로 주입받은 EntityManager 필드를 직접 사용해서 manager.persist(member), manager.find(Member.class, memberNo)를 호출한다.
7조회 전용 메서드에 @Transactional(readOnly = true)를 붙이면 좋은 이유는?
영속성 컨텍스트는 조회 시점의 스냅샷을 찍어두고 commit 시점에 변경 여부를 비교하는 변경 감지를 수행한다. 조회만 하고 끝낼 메서드라면 이 비교 작업 자체가 불필요한 비용이므로, readOnly=true로 생략할 수 있다.
