1POST /auth/login 요청을 처리하는 컨트롤러 메서드를 직접 만들지 않는데도 로그인이 동작하는 이유는?
우리가 만드는 것은 로그인 화면을 보여주는 GET /auth/login뿐이다. form이 POST로 전송되면 컨트롤러가 아닌 Security 필터가 가로채서 설정(formLogin)대로 처리한다.
2로그인할 때 입력한 비밀번호와 DB의 암호화된 비밀번호를 비교하는 주체는?
우리는 회원을 "조회"만 한다. AuthDetails.getPassword()가 돌려준 DB 비밀번호를 Security가 입력값과 직접 비교한다.
3AuthService.loadUserByUsername()에서 회원이 없을 때 해야 하는 일은?
예외를 던지면 AuthFailHandler로 넘어가고, 핸들러는 예외 타입으로 실패 원인 메시지를 구분한다. 회원이 있으면 AuthDetails로 감싸 반환하고, 그 객체가 세션에 저장된다.
4authorizeHttpRequests의 규칙에서 anyRequest().authenticated()를 맨 아래에 두는 이유는?
위에서부터 검사한다. anyRequest()가 위에 있으면 뒤의 구체적인 규칙(예: permitAll, /admin/*)이 의미를 잃고, 로그인 화면조차 로그인해야 열리는 상황이 생길 수 있다.
5AuthDetails에서 equals()와 hashCode()를 userId 기준으로 오버라이딩해야 하는 이유는?
SessionRegistry는 내부적으로 Map으로 사용자를 관리한다. equals()와 hashCode()는 반드시 같은 기준으로 함께 오버라이딩해야 한다. (현재 프로젝트에서는 아직 TODO로 남아 있다.)
6비밀번호를 5번 틀리면 계정이 잠기는 과정으로 맞는 것은?
횟수 증가는 User.increaseLoginFailCount() 도메인 메서드가 하고, 잠금 여부는 AuthDetails.isAccountNonLocked()로 Security에 전달된다. 로그인에 성공하면 횟수는 0으로 초기화된다.
7실패 횟수를 올리는 incrementLoginFailCount()에 save() 호출이 없는데도 UPDATE가 실행되는 이유는?
11/5에 배운 변경 감지가 그대로 쓰인 사례다. 값 변경은 Entity의 도메인 메서드가 하고, 저장은 영속성 컨텍스트가 처리한다.
8SecurityConfig의 csrf.disable()에 대한 설명으로 맞는 것은?
CSRF는 로그인한 사용자의 권한을 악용해 악성 사이트가 요청을 보내게 하는 공격이다. 세션 기반 인증에서는 보호가 필수이고, JWT 같은 Stateless 방식에서는 불필요하다고 프로젝트 주석에 적혀 있다.
