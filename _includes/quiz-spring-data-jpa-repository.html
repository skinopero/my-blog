1interface MenuRepository extends JpaRepository<Menu, Integer>처럼 선언만 하면 어떤 일이 일어날까?
JpaRepository<관리할 엔티티, @Id 타입>을 상속하면, 그 구현체(SimpleJpaRepository 등)를 Spring Data JPA가 런타임에 만들어 등록해준다. 11/2~11/3까지 직접 작성하던 Repository 클래스를 인터페이스 선언 한 줄로 대체할 수 있다.
2findByMenuPriceGreaterThanOrderByMenuPrice(int menuPrice) 같은 메서드를 무엇이라고 부를까?
메서드 이름의 조건식·정렬 규칙(GreaterThan, OrderBy 등)만으로 Spring Data JPA가 쿼리를 자동 생성해주는 기능을 쿼리 메서드라고 한다.
3쿼리 메서드의 단점으로 가장 알맞은 것은?
조건이 적을 땐 메서드 이름 하나로 편리하지만, 조건이 많아지거나 JOIN이 필요해지면 메서드 이름이 길어지고 정확한 의도를 파악하기 어려워진다.
4@Query(value = "...", nativeQuery = true)에서 nativeQuery를 생략하면 기본값은?
@Query의 기본값은 JPQL이다. 실제 DB 문법 그대로 쓰려면 nativeQuery = true를 명시해야 한다.
5menurepository.findById(menuCode)의 반환 타입이 Optional<Menu>인 이유는?
findById()는 Spring Data JPA가 미리 구현해둔 메서드로, 반환 타입이 Optional이기 때문에 없는 데이터를 조회해도 바로 에러로 끝나지 않고 orElseThrow() 등으로 원하는 예외를 직접 던질 수 있다.
6Menu 엔티티에 setter가 없고 changeMenuName(), stopSelling() 같은 이름 있는 메서드만 있는 이유는?
DTO는 화면에서 넘어온 값만 알고 DB에 저장된 현재 상태는 모르기 때문에 @Valid로는 상태 기반 규칙을 검사할 수 없다. 그래서 이런 규칙은 Entity가 이름 있는 메서드로 스스로 판단하도록 설계한다.
7MenuService의 책임 설명 중 맞는 것은?
자기 값만으로 판단 가능한 도메인 규칙은 Entity가, 조회가 필요한 비즈니스 규칙은 Policy가 맡고, Service는 그 순서만 조립한다. Entity는 Service 밖으로 나가지 않고 Controller에는 DTO만 전달된다.
8가격 검색 API에 @RequestParam과 함께 @Min(value = 0)을 붙여 백엔드에서도 검증하는 이유는?
프론트(JS) 유효성 검사는 URL 조작, body 조작 앞에서는 무력하다. 그래서 같은 검증을 백엔드에서도 반드시 다시 해야 한다.
