1SSR과 CSR을 가르는 가장 핵심적인 차이는?
MDN은 SSR을 "HTML을 서버에서 만드는 것", CSR을 "브라우저가 JavaScript로 마크업을 만드는 것"으로 설명한다. 핵심 질문은 "브라우저가 보는 HTML을 누가 완성하는가"다.
2Thymeleaf로 화면을 만드는 방식이 SSR인 이유는?
Spring MVC 컨트롤러가 뷰 이름을 돌려주면 서버가 HTML을 완성해서 응답한다. 링크를 누르면 서버에 새 HTML을 요청하고 페이지 전체가 바뀐다.
3Vite로 만든 React 프로젝트에 처음 접속하면 서버가 보내주는 것은?
CSR에서는 거의 빈 HTML과 JS를 받고, 브라우저에서 JS가 실행되어 화면(DOM)이 만들어진다. 그래서 처음 화면은 JS를 받아 실행해야 보인다.
4CSR에서 첫 화면이 그려진 뒤 화면을 갱신할 때 서버에서 받아 오는 것은?
MDN은 CSR의 장점으로 이후 갱신을 API로 받을 수 있어 앱 안의 이동이 빠르고 서버 부담이 적다는 점을 든다. 11/20에 fetch로 JSON을 받던 코드가 이 부분이다.
5SPA(Single Page Application)의 설명으로 알맞은 것은?
오늘 프로젝트에서는 index.html 하나만 받고, 주소가 바뀌면 Outlet 자리의 컴포넌트만 교체된다. MDN은 단점으로 SEO, 상태 유지와 내비게이션 구현의 수고, 성능 모니터링의 어려움을 든다.
6SPA와 CSR의 관계를 맞게 설명한 것은?
MDN의 설명이다. 오늘 배운 방식(Vite + React)은 "SPA이면서 CSR"인 조합이라고 이해하면 된다.
7Next에서 첫 방문 시 일어나는 hydration이란?
Next 공식 문서 기준으로, 첫 방문에서는 서버가 만든 HTML을 브라우저가 바로 보여주고, 이어서 클라이언트 컴포넌트를 hydration한다. 이후 이동은 클라이언트에서 처리한다.
8Next의 정적 렌더링과 동적 렌더링을 맞게 짝지은 것은?
사용자의 쿠키나 요청 헤더 같은 동적 함수를 쓰면 라우트가 동적 렌더링이 된다. 그래서 "Next는 SSR"이라는 키워드는 첫 HTML을 서버가 만든다는 큰 특징을 말하는 표현으로 이해한다.
